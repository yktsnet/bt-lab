# Design Decisions

[README](../README.md) の Design Decisions を圧縮せず、判断の全文をここに置く。「なぜそうしたか」だけでなく「なぜ別案にしなかったか」を辿れるようにする。

## 単一戦略の最適化でなく複数候補の継続的選抜を採る

1つの戦略をひたすらチューニングすると、その戦略が効かなくなった局面に気づく手段がない。パラメータを変えるたびに「良くなった」ように見えても、それが本当の改善か、たまたまその期間に噛み合っただけかを見分けられないからだ。

本リポは逆に、戦略候補を増やすことを前提に置いた。`strategies_md/`にkindを追加するたびにS2〜S8が全候補を再計算・再ランキングし、順位表の中で候補同士を相対評価する。1候補の絶対的な良し悪しではなく、他の候補と比べて生き残っているかどうかで判断できるようにするのが狙いで、これは「良い戦略を探す」のではなく「劣化を検知できる状態を維持する」ためのパイプラインである。

## カタログをSPEC.md(思想)とtemplate.py(実装)に分離する

機械可読な実装(`template.py`)だけをカタログにすると、パラメータの根拠や「このkindが効かない相場」が失われ、半年後に見返しても再現できない。逆に思想(`SPEC.md`)だけでは自動生成の入力にならない。

`strategies_md/HOWTO.md`はkindごとにこの2つを併置する規約を定め、`SPEC.md`には「思想」「親カテゴリでの位置」「パラメータ根拠」「弱点・留意点」の4セクションを必須にした。特に「親カテゴリでの位置」はカテゴリ内での重複を防ぐための項目で、これが無いと同じような仮説のkindが増殖し、Ban段で結局間引かれるだけの候補が積み上がる。

## エントリー率フィルタ + Jaccard重複排除でBanする(S4)

`PARAMS_GRID`の直積展開は、同じ思想に近いパラメータの組み合わせを大量に生む。素朴に全部を同じ土俵でランキングすると、相関の高い候補群が上位を占有し、ランキングの実質的な多様性が失われる。

S4はエントリー頻度が極端な候補(多すぎる/少なすぎる)を先に弾き、残った候補同士のエントリータイミングの重なり(Jaccard類似度)を見て、重複度が高い組を間引く。これによりS8のランキングに残る候補は「似ていない候補の中での勝ち残り」になり、単なるパラメータの偶然の一致が上位を占めることを防ぐ。

## ランキングはDDフィルタを通してからRecovery Factor基準にする(S8)

総pipsだけで順位をつけると、含み損の耐えられない候補(最大ドローダウンが大きい候補)が紛れ込む。総収益は高くても、運用に耐えられない候補を上位に出す意味は薄い。

S8は先にドローダウンでフィルタし、残った候補群の中でRecovery Factor(総収益 ÷ 最大ドローダウン)を基準に並べる。これは「儲かるか」より先に「壊れずに続けられるか」を選抜条件にする考え方で、bt-dynamicの「セルは成績でなく生存で選ぶ」と同じ発想を、戦略候補の選抜に適用したもの。

## 各段(S1b〜S8)を独立したCLIに分割する

パイプラインを1本のスクリプトにまとめると、パラメータを1つ変えるだけでも全段を再実行する必要があり、検証のたびに待ち時間が積み上がる。特にS1b/S1c(データ変換・特徴量計算)はパラメータに依存せず、S5(TP/SL判定)だけを変えて回したい場面が大半を占める。

`core/`配下は各段を独立したCLIとして実装し、`bt.py`はそれらをサブプロセスとして束ねる薄い配線層に徹する。副作用として各段の出力(`parquet_data/`, `positions/`, `pos_events/`, `rank/`等)がファイルとして残り、途中結果の検査やデバッグにも使える。

## パイプライン本体は戦略の中身をimportしない

`core/`・`lib/`が個々の戦略kindのロジックを直接importする設計にすると、戦略を1つ追加するたびにエンジン側のコードにも変更が要る。これでは戦略とエンジンが密結合し、カタログを増やすリスクがエンジンの安定性に波及する。

`s2_gen_strategies`は`strategies_md/<kind>/template.py`を動的に読み込んで`strategies/<kind>/<slug>.py`を生成するだけで、`core/`・`lib/`側は生成されたファイルの出力規約(`entry_flag`/`buy_sell`/`trend_dir`の3カラム)だけを知っていればよい。この一方向依存により、戦略を何個追加してもエンジン側の変更は不要になる。

## 実データ・実カタログは同梱しない

`examples/sample/`は乱数ウォークで生成した合成OHLCデータのみを持ち、`strategies_md/`には教科書的なダミーkind(`oscillator/rsi_zone`)を1つだけ置く。実運用のカタログ・実データ・成績は非公開の研究環境側にのみ存在し、このリポには構造的に存在しない。

これはbt-dynamicが対応表の実数をconfig JSONの外部注入として構造的に排除したのと同じ発想を、戦略カタログというファイル群のレベルで適用したもの。パイプラインの仕組みを検証するのに実データは要らないため、公開/非公開の線引きと技術的な必要性が一致している。
